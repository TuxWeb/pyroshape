# TOTP authentication for Pyroshape

Status: Proposed. This specification defines the first implementation. Each application opts in to enrollment, then each user chooses whether to enroll.

## Scope and current behavior

Core owns TOTP verification, enrollment, replacement, recovery, and session issuance. The SvelteKit starter supplies the account security page and two-step login. Consuming SPAs use the same JSON API and cookies with any frontend framework. The first version supports one authenticator secret and one offline recovery code per account. Existing email verification and password policies continue to apply.

Today `AuthService::login()` verifies the password and account status, writes a refresh-token record, and issues the login cookie. `CheckValidAuthToken` and `RequireAuth` serve ordinary authenticated routes. Password change already checks the current refresh token against the database and requires the password. Reuse those boundaries. Put the second-factor decision inside the auth service, so direct calls to `AuthService::login()` also require TOTP, and keep ordinary requests on the existing stateless path. ## HTTP contract

These are same-origin JSON endpoints under the application's configured base path. Responses that carry auth state, provisioning data, or recovery material use `Cache-Control: no-store`. Preserve the existing success response and login cookie for completed authentication. Errors retain `error.message` and add a stable `error.code` for the new decisions. A `202` response always has `authenticated: false`. Only `200` from a completed login has `authenticated: true`.

| Method and path | Request and authorization | Success |
| --- | --- | --- |
| `POST /api/auth/login` | Existing `email`, `password`, `rememberMe`. | `200` with the existing session for a user without TOTP. For a user with TOTP, `202` with `next: totp_required`, `flowId`, and `expiresAt`. Set a separate challenge cookie. |
| `POST /api/auth/login/totp` | `flowId` and `code` as a six-character digit string. Requires the matching challenge cookie. | `200` with the existing login response. Consume the challenge and clear its cookie. |
| `GET /api/auth/totp` | Require a current session. | `200` with `enrollmentAvailable`, `enabled`, `enabledAt`, and `disabledAt`. Dates are UTC ISO 8601 strings or `null`. |
| `POST /api/auth/totp/setup` | Current session and `currentPassword`. If a factor is already active, also require its current `code`. | `200` with `flowId`, `expiresAt`, `provisioningUri`, and `manualKey` for a new candidate. The current factor remains in force. |
| `POST /api/auth/totp/setup/confirm` | Current session, `flowId`, and a `code` from the candidate authenticator. | `200` with updated TOTP status, `recoveryCode`, and `reauthenticationRequired: true`. |
| `POST /api/auth/totp/disable` | Current session, `currentPassword`, and current `code`. | `200` with disabled status and `reauthenticationRequired: true`. |
| `POST /api/auth/totp/recovery` | `flowId` from the password step, matching challenge cookie, and `recoveryCode`. | `200` with `flowId`, `expiresAt`, `provisioningUri`, and `manualKey` for a replacement. Set a new challenge cookie for the recovery flow. |
| `POST /api/auth/totp/recovery/confirm` | Recovery `flowId`, its challenge cookie, and a `code` from the replacement. | `200` with active status, a new `recoveryCode`, and `reauthenticationRequired: true`. The user signs in with the replacement authenticator. |

Keep the current invalid-password and unavailable-account responses. For new endpoints use `400 invalid_request` for malformed input, `401 invalid_code` for a failed factor proof, `401 invalid_credentials` for failed password reauthentication, `401 current_session_required` for a missing or revoked session, and `403 origin_rejected` for wrong or missing browser origin. Return `409 flow_unavailable` for expired, consumed, superseded, or mismatched flows and `409 enrollment_unavailable` when setup is closed for an unenrolled user. Return `429 rate_limited` with `Retry-After` for throttling and a generic `503 auth_unavailable` when required persistence or key material is unavailable. Error responses omit secrets, raw tokens, and account details unavailable to the caller.

The challenge cookie is host-only, `Secure` in production, `HttpOnly`, `SameSite=Strict`, and scoped to `/api/auth` under the application's configured base path. Use a separate name from the login cookie. Its value is a random 32-byte bearer credential. The separate opaque `flowId` prevents mixed-tab submissions from acting on the wrong account. Each stage binds the purpose, user, expiry, current account version, and the original `rememberMe` value for login. Login challenges expire after five minutes. Setup and recovery candidates expire after ten minutes. Close the presented challenge on logout or successful password-only login and clear its cookie with the same path and attributes. Closing a form discards the SPA state. Server-side expiry and bounded cleanup handle abandoned flows.

## Core and middleware

- Keep the public `AuthService::login()` signature. Return a pending outcome for enrolled users and update the controller to branch on the outcome before logging success. Document the new branch for direct callers and for consuming SPAs. Complete password-only and second-factor logins through one session issuance path.
- Extract current refresh-session validation from `AuthService` and expose a route-scoped middleware for authenticated TOTP management. It checks the presented refresh token, its stored hash and revocation status, and the current account. It passes a verified user ID and session identity to the handler. It performs neither token rotation nor cookie renewal. Keep the password-change behavior while sharing its underlying validation.
- Use route-scoped same-origin middleware for TOTP writes and cookie-bound login or recovery steps. Reuse the same origin check before the first login step writes a challenge or sets its cookie. Validate the deployment's public origin, deriving it from forwarded headers only when the proxy is trusted. Require JSON on the new POST endpoints. Preserve the existing password-only login contract. Register the new API routes before the SPA fallback and keep authentication middleware out of static asset routes.
- TOTP verification and persistence belong in services behind the controllers. Application routes with sensitive business effects may reuse the current-session middleware and must still check current authorization and ownership. The access JWT supplies identity during its remaining lifetime; it does not establish that those checks still pass. [Session contract](../../skills/pyroshape-app/references/core-contracts.md#stateless-sessions-and-forced-logout)
- Use a fixed RFC 6238 profile for the first version: six digits, a 30-second interval, and HMAC-SHA-1 for authenticator interoperability. Accept the current interval and at most one adjacent interval in each direction. Keep the server clock synchronized and inject a testable clock. Evaluate the matched interval and consume it atomically across login and account management. Select a currently supported, audited Composer dependency such as OTPHP during implementation and run the dependency advisory check against the resolved lockfiles. [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html) · [OTPHP](https://github.com/Spomky-Labs/otphp) · [NIST SP 800-63B, OTP authenticators](https://pages.nist.gov/800-63-4/sp800-63b.html#otp)
- Persist failed second-factor attempts per flow and across flows per account. Expire a flow after five failures, and allow ten failures per account during a fifteen-minute window starting with the first failure. Enforce the account limit on setup, confirmation, disable, and both login and recovery paths. Issuing another challenge does not reset the account limit. Require a shared ingress or application rate limit per client IP on auth endpoints and document the recipe for multi-instance deployments. Commit failed-attempt counters even when the authentication attempt is rejected.

## Persistence and concurrency

Apply additive migrations to the deployed schema. Use the existing UTC timestamp conventions, PostgreSQL `BOOLEAN`, and the MySQL/MariaDB boolean equivalent. Existing rows start unenrolled. Add the following fields to `users`.

| Field | Meaning |
| --- | --- |
| `totp_enabled` | Required boolean, default `false`. |
| `totp_secret_encrypted` | Nullable, versioned authenticated ciphertext for the active seed. Required while enabled and cleared on disable. |
| `totp_enabled_at`, `totp_disabled_at` | Nullable UTC timestamps for the most recent enable and disable. Replacing the authenticator on an enabled account preserves the enable date. |
| `totp_last_used_step` | Nullable 64-bit interval number for the active seed. On enrollment or replacement, initialize it to the interval used to confirm that seed. |
| `totp_recovery_code_hash` | Nullable hash of the one-time offline recovery code. Replace it on successful enrollment, recovery, or authenticator replacement. Clear it on disable. |
| `auth_version` | Monotonic integer starting at zero. Increment for password changes and factor changes. Account integrations must increment it when changing login eligibility. Bind pending auth flows to the version checked at creation. |

Use one `auth_totp_flows` table for login, setup, and recovery. Store a unique flow ID, user foreign key with cascade on deletion, purpose, account version, expiry, consumption time, failed-attempt count, and only the fields needed for that purpose. Those fields are the hash of the cookie credential for login or recovery, the initiating refresh-token identity for authenticated setup, `rememberMe` for login, and the encrypted candidate for setup or recovery. Store account-level throttle state in a small row keyed by user ID. Index expiry for bounded cleanup and active flows by user. Erase candidate ciphertext when consumed or canceled. Keep candidate reads separate from ordinary profile and session queries. Explicitly exclude all TOTP secrets and hashes from claims, user payloads, diagnostics, and logs.

Encrypt seeds and candidates with AES-256-GCM and a dedicated per-application key kept outside the database. Use a versioned envelope with key ID, a fresh 12-byte random nonce, and a 16-byte authentication tag. Reject malformed envelopes before decrypting. Bind ciphertext to its user and purpose. Document key distribution, rotation, and restore. Use a random 160-bit seed unique per enrollment and a recovery code with at least 128 bits of randomness. The `otpauth://` URI uses a stable application issuer, the account label, and a Base32 secret for manual entry. Render the QR locally in the SPA. Exclude provisioning payloads and recovery codes from HTTP request URLs, browser storage, analytics, logs, and third-party QR services. [RFC 6238, security considerations](https://www.rfc-editor.org/rfc/rfc6238.html#section-5) · [Authenticator key URI format](https://github.com/google/google-authenticator/wiki/Key-Uri-Format) · [NIST SP 800-63B, authenticator events](https://pages.nist.gov/800-63-4/sp800-63b/events/)

Use short transactions on one PDO connection. Lock the same user row first and follow a consistent lock order for flow and refresh records. Recheck account version, active factor, and relevant authorization inside the transaction. Verify expensive password hashes before acquiring locks, then recheck their observed state under the lock. Require the matched TOTP interval to advance the persisted interval. Commit the interval, consumed flow, and new refresh record together on login. Set cookies and report success only after commit. Authenticated setup is bound to the initiating refresh JTI. If normal renewal rotates that JTI, reject setup confirmation and ask the user to restart it.

During factor activation, replacement, recovery, or disable, update the user row, close outstanding flows, and revoke all current refresh records in the same transaction. Clear the current browser's login cookie on success. Serialize password-only issuance and refresh rotation with factor mutation and revalidate the source refresh record under the lock before rotating it. Otherwise a concurrent refresh could create a usable successor after revocation. Ordinary access-token validation receives no new database lookup. A previously issued access JWT can still be valid on ordinary routes until expiry, including configured skew. [Current refresh flow](../../src/Auth/AuthService.php) · [User repository](../../src/Auth/UserRepository.php)

## Recovery and SPA behavior

Offer recovery only after successful password verification. A valid backup code consumes the password challenge and opens a restricted enrollment flow without issuing an authenticated session or disabling the current factor. Bind that flow to the proof already verified and allow one unexpired authorized recovery flow per user. Consume the old recovery code and replace the factor only when the new authenticator proves possession. If enrollment expires before confirmation, the account retains its old factor and recovery code. Concurrent confirmations can commit only once. Display the replacement recovery code once after success and instruct the user to save it before signing in again. A user who still has access to the current authenticator can run authenticated setup and replacement again to obtain a new recovery code. For a lost device and missing recovery code, the consuming application owns its manual identity-verification policy. Core provides no email-only bypass.

Reuse the starter's typed JSON client and session store. In the login form, branch on the response body after the password step, clear the password, and keep `flowId` in component memory only. Show a text field with a numeric keypad and one-time-code autocomplete so leading zeroes survive, plus a separate recovery option. Handle expiry by returning to the password step. Refresh the normal session store only after authenticated success. Leave the current login path in place for apps whose users have never enrolled. [Starter login](../../apps/skeleton/frontend/src/routes/login/+page.svelte) · [API client](../../apps/skeleton/frontend/src/lib/api.ts)

Add an `/account/security` page with status and dates, setup and replacement, QR with a manual entry alternative, confirmation, and separately confirmed disable. Hold provisioned data in component memory and clear it on success, cancellation, or navigation. Clear the SPA session store after a factor change, show any newly issued recovery code before navigating away, and then return to sign-in. The setup confirmation interval has already been used, so prompt the user to wait for the next code when signing in immediately. Update the demo login form to distinguish `202` from authenticated success as well. [Demo login](../../apps/demo/frontend/src/routes/login/+page.svelte)

## Rollout and acceptance

1. Add separate numbered migrations for MySQL/MariaDB and PostgreSQL in Core and the applicable bundled app migration directories. Cover existing installations and fresh installs. Continue to support a known unmigrated schema with enrollment unavailable and no enrolled accounts. A missing field in a custom repository or a database error must not silently convert a migrated account to password-only auth. Use `settings.auth.totp.allowEnrollment` to open enrollment after migration and key checks, with a default of `false`. Enforce the persisted flag independently of that setting. Closing enrollment leaves maintenance and recovery available for enrolled users. [MySQL baseline](../../database/migrations/001_auth_schema.sql) · [Starter PostgreSQL baseline](../../apps/skeleton/database/migrations/postgresql/001_auth_schema.sql)
2. Apply migrations and deploy a compatible backend and SPA on all serving instances before opening enrollment. Provision the same keys and throttling policy across instances. After enrollment opens, roll back only to a build that still enforces TOTP. Emit audit events for enrollment, replacement, disable, recovery, and throttling with outcome and safe identifiers. Document how the consuming app can deliver factor-change and recovery notifications through its existing verified channel. After restoring an older database snapshot, invalidate pending flows and sessions, reconcile factor changes, and reissue affected recovery codes before resuming sign-in. [Production deployment guide](../operations/deploy-app.md)
3. Verify three focused scenarios through real HTTP entry points. Use isolated databases and a controllable clock. Run persistence and transaction cases with two independent PDO connections on PostgreSQL, MySQL, and MariaDB. Test rollback after a verification succeeds but before the session writes commit. Check the built SvelteKit SPA in a browser.

| Scenario | Acceptance criteria |
| --- | --- |
| Existing login and rollout | Upgraded accounts default to disabled. Existing login, session and cookie contract still works with enrollment closed and before migration. Enrollment fails closed on misconfiguration. An enrolled user still needs TOTP when enrollment closes. Ordinary access checks stay stateless. |
| TOTP login and concurrency | Password-only step issues no login cookie for an enrolled account. A valid second step works and honors `rememberMe`. Wrong, expired, repeated, and concurrent codes or challenges do not create extra sessions. A password or account change invalidates pending flows. Rate limits apply across flows. |
| Account lifecycle | Setup, local QR/manual entry, replacement, disable, and one-use recovery work in the SPA. Expiry and cancellation leave the active factor usable. Concurrent factor mutations or refresh cannot leave an old refresh session usable. Access tokens with revoked refresh sessions are rejected on sensitive routes. Secrets stay out of logs and regular API responses. |
