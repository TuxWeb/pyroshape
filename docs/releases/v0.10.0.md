# Pyroshape 0.10.0

Pyroshape 0.10.0 adds optional time-based one-time passwords (TOTP) for password-authenticated accounts. To offer TOTP, apply the database migration and deploy a compatible backend and SPA before opening enrollment. Existing users start with TOTP disabled and keep their existing login flow until they enroll.

## New functionality

- Core supports enrollment, status, factor replacement, disable, and device recovery. The user receives one offline recovery code when they confirm an authenticator. Recovery requires the account password and a saved code, then validates the replacement authenticator before it switches the account over.
- Enrolled users sign in in two steps. The password endpoint returns `202` with `authenticated: false` and a brief challenge. The second step verifies the authenticator and issues the existing encrypted session cookie. The starter includes **Account security**, a locally rendered QR code, a manual setup key, and the recovery flow. The demo recognizes the second step in its login form. [API contract](../specs/totp-authentication.md#http-contract)
- Core prevents reuse of an accepted time interval and limits failed second-factor attempts across challenges. Factor changes revoke the user's refresh sessions in the same transaction, coordinated with refresh rotation. Sensitive routes can use `RequireCurrentSession` to check current session validity with no cookie renewal. The demo's project and task deletions show that middleware in use. Ordinary access-token checks stay stateless. [Session contract](../../skills/pyroshape-app/references/core-contracts.md#stateless-sessions-and-forced-logout)
- Composer installs `pyroshape-prune-totp.php` for scheduled, bounded cleanup of expired challenges and pending authenticator setups.

## Database migration required for TOTP

Use **one** migration for the application's schema and database engine. Back up the database and verify the restore procedure. For an existing installation, apply only the new migration to the database that already contains the app's auth tables. On a fresh install, apply the baseline first, then the TOTP migration. Keep an independent migration record for each database.

| Installation | PostgreSQL | MySQL or MariaDB |
| --- | --- | --- |
| Composer Core package | [`database/migrations/postgresql/002_auth_totp.sql`](../../database/migrations/postgresql/002_auth_totp.sql) | [`database/migrations/002_auth_totp.sql`](../../database/migrations/002_auth_totp.sql) |
| Starter app, relative to `apps/skeleton` | [`database/migrations/postgresql/002_auth_totp.sql`](../../apps/skeleton/database/migrations/postgresql/002_auth_totp.sql) | [`database/migrations/002_auth_totp.sql`](../../apps/skeleton/database/migrations/002_auth_totp.sql) |
| Demo app, relative to `apps/demo` |  | [`database/migrations/003_auth_totp.sql`](../../apps/demo/database/migrations/003_auth_totp.sql), after `002_projects_tasks_schema.sql` |

Core includes `001_auth_schema.sql` for fresh installations under `database/migrations/` for MySQL/MariaDB and `database/migrations/postgresql/` for PostgreSQL. When using the Composer package, look for `database/migrations/` under `vendor/tuxweb-it/pyroshape/`.

| Table | Migration effect | Purpose |
| --- | --- | --- |
| `users` | Adds `totp_enabled`, `totp_secret_encrypted`, `totp_enabled_at`, `totp_disabled_at`, `totp_last_used_step`, `totp_recovery_code_hash`, and `auth_version`. | Stores the current TOTP status, encrypted authenticator secret, activation dates, replay protection, and hashed offline recovery code. `auth_version` invalidates pending flows when credentials or account eligibility change. |
| `auth_totp_flows` | Creates a table indexed by expiry and user, with a foreign key to `users`. | Stores short-lived login, setup, and recovery challenges. Cookie credentials are hashed and candidate secrets are encrypted. |
| `auth_totp_throttle` | Creates a table with one row per user. | Shares the failed-attempt budget across challenges and PHP workers. |
| `auth_tokens` | Uses the existing `revocation_time` column. | Revokes the current and prior refresh sessions when the factor changes. |

Before exposing enrollment, verify that the runtime database role can read the new columns and tables and can insert, update, and delete the required rows. The migration uses a schema owner or a dedicated migration role. With a custom `UserRepository`, preserve the stored factor state and use the shared user locking and versioning rules. Password changes and application-owned changes to login eligibility must invalidate pending flows. [Persistence contract](../specs/totp-authentication.md#persistence-and-concurrency)

## Enable enrollment

1. Apply the migration, then deploy Core 0.10.0 and an updated SPA across all serving instances. With a custom frontend, handle the JSON `202` branch before updating the session store or navigating. As a smoke check, verify login with an unenrolled account before opening enrollment. Callers using `AuthService::login()` directly must check `authenticated === true`. Overrides that add login policy should delegate the final authentication decision to Core. [API contract](../specs/totp-authentication.md#http-contract)
2. Configure the same public origin, issuer, and encryption keyring on all instances. Use HTTPS and a synchronized system clock. If a proxy terminates TLS, configure the actual browser origin explicitly, with scheme, host, and any non-default port. Keep the keyring in deployment secrets, separate from the existing JWT and cookie keys.
3. Configure a shared per-client-IP limit on `/api/auth/*` at the application's ingress, including any base path. Key it by the client IP established by your trusted proxy chain and return `429` on excess requests. For instance, start with 20 requests per minute and allow a short burst. If several ingress instances accept requests, use a shared counter or a common throttling tier. Core separately provides the durable per-account and per-flow TOTP limits.
4. Schedule expired-flow cleanup using the same app configuration and runtime database permissions as the web app. Each invocation removes at most the requested batch size. Run it regularly and monitor its exit status. The command below removes up to 100 expired rows.

   ```sh
   php vendor/bin/pyroshape-prune-totp.php config/config.php 100
   ```

5. Open enrollment and test with an isolated smoke account. Verify QR or manual setup, failed and successful second-factor attempts, status, recovery, and disable. Confirm that an older browser session can no longer renew or use sensitive routes after any factor change. Use the output from the actual deployed SPA and origin for these checks.

The bundled apps read the following environment variables. Applications with their own configuration can supply the equivalent values under `settings.auth.totp`.

| Variable | Meaning |
| --- | --- |
| `PYROSHAPE_TOTP_ALLOW_ENROLLMENT` | Set to `1` to open enrollment. Unset it or set it to `0` to close enrollment. Existing enrolled accounts still require TOTP and can manage or recover their factor. |
| `PYROSHAPE_TOTP_ISSUER` | The stable label users see in their authenticator. Choose the deployed application's name and omit colons. |
| `PYROSHAPE_TOTP_KEY_ID` | Identifies the active encryption key in the keyring. Use 1–32 letters, digits, underscores, or hyphens. |
| `PYROSHAPE_TOTP_KEYS` | JSON object mapping key IDs to standard Base64 strings, each encoding 32 random bytes. Generate the value for a key with `openssl rand -base64 32` in your secret management workflow. |
| `PYROSHAPE_TOTP_PUBLIC_ORIGIN` | Browser origin, for example `https://app.example.test`. Omit the path and trailing slash. This supports same-origin checks when the PHP request URI reflects an internal proxy hop. |

## Key rotation and rollback

Add the new key to every instance before changing the active key ID. Keep the old keys available for decryption while any enrolled user, pending flow, or retained backup depends on them. Replacing a user's authenticator encrypts that user's new seed with the active key. Retire an old key only after the remaining seeds have been replaced or re-encrypted and the relevant restore window has passed.

When diagnosing an enrollment problem, close enrollment first. Once any user is enrolled, a code rollback must continue to enforce that factor. Keep the schema and keyring in place. If restoring an older database snapshot, review the status of enrollments and credential changes, invalidate restored refresh sessions and pending flows, and reconcile affected recovery codes before resuming sign-in. Use the application's verified notification channel for factor changes and recovery when available. [Production deployment guide](../operations/deploy-app.md)
